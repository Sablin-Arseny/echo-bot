# Echo

**Echo** --- автоматизированная система для организации совместных
мероприятий и учёта общих расходов. Пользователь взаимодействует с
системой через бота, который объединяет в одном интерфейсе работу с
группами, мероприятиями, участниками и финансовыми обязательствами.

Проект разрабатывается в рамках учебной работы по сбору, анализу и
реализации требований к программному обеспечению.

## Назначение

При организации совместных мероприятий информация часто распределяется
между разными чатами и инструментами: отдельно обсуждаются участники и
детали мероприятия, отдельно фиксируются расходы и рассчитывается, кто
кому должен.

Echo предназначен для объединения этих процессов в одной системе и
сокращения объёма ручных действий.

Основной пользовательский сценарий:

`пользователь → группа → мероприятие → участники → расходы → расчёт взаимных обязательств`

## Основные возможности

В соответствии с требованиями проекта система предусматривает:

-   регистрацию и идентификацию пользователей;
-   создание групп и вступление в существующие группы;
-   создание и управление мероприятиями;
-   добавление участников мероприятий;
-   добавление и корректировку расходов;
-   хранение информации о расходах;
-   автоматический пересчёт взаимных финансовых обязательств после
    изменения расходов;
-   просмотр актуальной информации о мероприятии;
-   проверку прав доступа пользователя к группам, мероприятиям и
    связанным данным;
-   взаимодействие с пользователем через бот-интерфейс.

> Проект находится в разработке. Часть перечисленной функциональности
> может быть запланирована техническим заданием и ещё не присутствовать
> в текущей версии приложения.

## Архитектура

Целевая архитектура Echo строится по клиент-серверному принципу и
логически разделяется на три уровня:

1.  **Bot / пользовательский интерфейс** --- принимает действия
    пользователя и отображает результаты.
2.  **Бизнес-логика** --- проверяет данные и права доступа, выполняет
    операции с группами, мероприятиями и расходами, рассчитывает
    обязательства.
3.  **Хранение данных** --- обеспечивает сохранение пользователей,
    групп, мероприятий, участников и финансовых данных.

На начальном этапе проект предполагает модульную монолитную архитектуру
с возможностью дальнейшего выделения отдельных компонентов в
самостоятельные сервисы.

``` text
Пользователь
     │
     ▼
    Бот
     │
     ▼
Бизнес-логика
     │
     ▼
База данных
```

## Основные сущности

Предметная область системы включает следующие основные объекты:

-   **User** --- пользователь системы;
-   **Group** --- группа пользователей;
-   **Group Member** --- участник группы;
-   **Event** --- совместное мероприятие;
-   **Event Member** --- участник мероприятия;
-   **Expense** --- расход;
-   **Financial Obligation** --- рассчитанное финансовое обязательство
    между участниками.

Пользователь может состоять в нескольких группах, группа может содержать
несколько мероприятий, а мероприятие --- нескольких участников и
расходов.

## Технологии

В текущем репозитории используются Python-библиотеки для конфигурации
приложения и работы с данными:

-   **Python**;
-   **SQLAlchemy 2** --- работа с базой данных;
-   **asyncpg** --- асинхронное подключение к PostgreSQL;
-   **Pydantic / pydantic-settings** --- модели данных и конфигурация;
-   **pdoc** --- генерация документации.

В целевой архитектуре техническим заданием также предусмотрено
использование **PostgreSQL** для хранения данных.

## Логика работы с расходами

Один из ключевых сценариев Echo связан с совместными расходами:

``` text
Выбор мероприятия
        ↓
Добавление расхода
        ↓
Проверка введённых данных
        ↓
Сохранение расхода
        ↓
Определение участников расхода
        ↓
Расчёт взаимных обязательств
        ↓
Отображение результата
```

При корректировке ранее созданного расхода финансовые обязательства
должны рассчитываться повторно на основании актуальных данных.

## Требования к безопасности и надёжности

В проекте предусмотрены следующие базовые требования:

-   идентификация пользователя перед предоставлением доступа к данным;
-   проверка прав доступа на стороне серверной логики;
-   отсутствие токенов, паролей и других секретов в исходном коде;
-   запрет на запись секретных данных в открытом виде в журналы;
-   сохранность ранее записанных данных при ошибках обработки отдельных
    запросов;
-   защита данных разных пользователей друг от друга;
-   возможность резервного копирования базы данных.
